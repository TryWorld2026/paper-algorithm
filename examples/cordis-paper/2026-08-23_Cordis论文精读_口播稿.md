# Cordis 论文精读

## 开场

8 月 13 号晚上，DeepSeek 把 Harness 开了源，开发者圈热闹了一整晚。很少有人注意到，同一天，GitHub 上还挂出来一篇论文，整整八十八页，通篇在讲一个听起来跟 AI 毫无关系的题目，软件零件怎么随装随卸还不出乱子。论文一共三位作者，单位栏里只有两个名字，北京大学和 DeepSeek，第一作者两边都挂了职，其中一位你可能有印象，崔添翼，上期讲过，他就是 Harness 项目的负责人。顺带交代一下两家的关系。Cordis 的入门读物就挂在 DeepSeek 的 GitHub 页面底下，代码互相串门。这篇论文，算是把两家共用的那张图纸正式画了出来。上一期我们把 Harness 拆开看过，今天补上它脚底下最硬的那块，把这篇论文读一遍。公式我一个都不念，只讲它在干什么，跟你有什么关系。

## 第一层 装容易，卸难

论文开头没谈 AI，它先挑了个所有人都用过的软件开刀，VSCode。装插件有多爽，卸插件就有多别扭。论文统计了安装量排前一百的 VSCode 扩展，八十七个带可执行代码，这类扩展一旦你想卸载，多半得把整个宿主进程重启，所有扩展跟着陪跑。VSCode 其实留了一个卸载回调，可它只在宿主进程整体关闭的时候才被调用，运行中想单独摘掉哪个扩展，它帮不上忙。另一个数字更冷清，这一百个扩展里，声明过相互依赖关系的只有七个。装的时候大家抢着上，卸的时候谁也摘不干净。

问题出在哪。现在的软件对付拆装，靠三招，功能不够就加个插件，插件管不了就重启进程，再大的事交给容器编排去调度服务。这三招都糙。重启进程，攒了几小时的缓存和连接全没了，重建要几秒到几分钟，为了顶住这段空档，还得额外养一批备份实例，钱就烧在这。容器呢，只能管到机器和服务那一层，同一个程序内部谁依赖谁，它看不见，本来一次函数调用就能搞定的事，非得绕一圈网络。论文给这类毛病起了个总称呼，动态组合的问题。零件要在运行时装上去、拆下来、改配置，这件事天天在发生，可它的理论底子薄得可怜，跟静态组装那套成熟理论比，差着几十年的功课。

## 第二层 两个维度

论文说，要把零件拆干净，得同时做到两件事。第一件跟时间有关，叫时间可组合。一个组件被卸掉的时候，它对系统做过的每处改动都得能原样撤回。登记过的资源要释放，注册过的事件要注销，一样都不能留。第二件跟空间有关，叫空间可组合。组件之间可以声明我需要谁，环境一变，系统能自动把消息送到。

这两件事听着像常识，工程里一直做不利索，原因也简单，缺趁手的工具。论文从几十年前的编程语言理论里翻出两件老古董，一个叫效应，记录程序对环境做了什么，一个叫余效应，记录程序要求环境提供什么。这两个概念以前只在编译阶段用，做静态检查。为什么非得搬进运行时，道理不复杂，插件是部署之后才装进来的，任何编译期的检查都够不着它。所以这篇论文干的活，是把它们搬进运行时，让程序跑着的时候也能记账。

搬过去之后长这样。效应变成可回滚的，每个操作执行时都得交出一个逆操作，运行时替你收着，像收银条一样攒起来，卸载的时候按后进先出的顺序挨个执行，做过什么就撤销什么。余效应变成响应式的。组件开工前先声明我要哪些服务。环境一变，运行时按声明逐个核对，该激活的激活，该停用的停用，跟它不相干的组件毫无察觉。

拿聊天机器人想象一下这个画面。聊天平台的适配器负责收发消息，数据库驱动负责存数据，功能插件把这两样声明成自己的需要。半夜适配器掉线了，依赖它的插件安静地停在那等着，不报错也不崩，通道一恢复，它们自己活过来接着干。今天绝大多数软件做不到这么体面。

## 第三层 数学怎么兜底

光有机制还不够，凭什么信它拆得干净。八十八页里最重的部分就在这。论文把上面这套东西写成一个演算，等于给动态组装这门手艺配了一套运算规则，然后一条一条证明。单个组件卸载之后，上下文能恢复原状，这是局部性质。更难的地方在整体，几十上百个组件交错运行，你卸一个，牵动一圈依赖，论文的元理论证明了，局部性质在这种连锁反应下依然成立，整个系统不会因为一次拆卸进入说不清的状态。

设计里还有一步很要紧。效应和余效应本来是两本账，一本记你改了什么，一本记你要什么。论文把这两本账合成了一本，就是同一个上下文。写过插件的人对它不陌生，装和卸能咬合得这么紧，靠的就是这个合并。热替换也做了同样的处理，新代码加载失败，系统按事务回滚到加载前的样子，永远不会卡在一半新一半旧的状态里。流程写得像流水账。先按依赖关系把改动过的模块分堆，能替换的一堆，动不了的一堆。卷进循环引用拿不准的，一律按不能替换处理，宁可重启也不冒险。然后找出所有被波及的组件，备份旧模块，逐个换新。任何一步失败，整批退回原样。

## 第四层 落地在哪里

理论要落地才算数。这套思想的实现叫 Cordis，分三层。最底下是核心库，所有对环境的改动都从同一个入口走，走这个入口就自动记账。中间是组件加载器，负责读配置、协调依赖、热替换模块。最上面才是具体应用。

最有说服力的案例是一个叫 Koishi 的聊天机器人框架，在这套核心上跑了四年多，社区贡献的插件超过四千个。四千个什么概念，你一天试装十个，得连试一年多。运行中换数据库后端，只有依赖它的那几个插件重启，其余照常运转。开发时改代码保存，热替换当场生效，别处的连接不掉线。四千个互不相识的作者写的插件能这样拼在一起，靠的就是前面那套声明加通知的机制。

还有个细节能说明这套东西有多不挑场景。Koishi 的网页控制台，本身就是另一个独立的 Cordis 应用，同一套模型在浏览器里再跑一遍，管的从消息和数据库换成了页面和按钮。论文拿这个当证据，说明它给出的只是一套通用的组装规则，具体拿来组装什么，随你。

DeepSeek 的 Harness 也压在这套框架上。上一期讲过它的口号，一切皆插件。当时我说连模型本身都是插件，主循环也能换，现在可以把底气说清楚了，换和撤这两个动作，背后各有一套被数学证明过的机制托着。论文引言里还交代了动机，未来的 Agent 要能一边干活一边改装自己。自己给自己动手术这种事，没有可回滚和自动通知这两样保命机制，改一次就得宕机一回。

## 第五层 别急着神化

边界也得划清楚。第一，运行时只负责记账和执行逆操作，你交上来的逆操作是不是真能把事情还原，框架查不了，责任还在写插件的人。第二，论文自己承认，Koishi 这个案例属于观察性质的证据，证明了这条路走得通、有人走，没有跟别的架构做定量对比，这套机制本身开销多大，还是空白。第三，实现还年轻，Koishi 目前跑的还是第三代，论文讲的是第四代，官方文档明说了接口随时可能变。顺带一提，论文自己也标着草稿两个字，仓库里写明还在改，八十八页是今天的模样，下个月可能就不一样了。

## 收尾

读完这篇论文，我最大的感受是这个行业的分工在变细。以前大家比谁的模型聪明，现在有人开始给 Agent 时代写基础理论了，八十八页里没有一行提示词，讲的全是零件怎么装上去、怎么拆下来、拆完怎么不留痕迹。这类工作短期看不见回报，可让软件能安全地自我改造，早晚绕不开它。论文全文挂在 GitHub 上，搜 cordiverse 就能找到，敢啃的可以去啃原文。你觉得给软件写基础理论这件事值不值一个星标，评论区聊聊。
